# Web UI development

Work on the React single-page app embedded at `GET /ui`.

## Prerequisites

- [pnpm](https://pnpm.io) installed.
- A `tn serve` daemon running somewhere you can point the dev server at (its `/status` and `/events` are what the app renders).

## Setup and dev server

```bash
cd webui
pnpm install
pnpm dev
```

This starts Vite's dev server. `vite.config.ts` sets `base: '/ui/'` (matching the path the daemon mounts the built app at) and has no dev proxy configured: the app calls the daemon directly at `window.location.origin` (see `bridgeUrl()` in `src/lib/api.ts`), which resolves correctly once the daemon serves the built bundle itself, but during `pnpm dev` you're on Vite's own dev origin, not the daemon's. If you need the dev server to talk to a daemon on a different origin during local development, you'll need to either run the daemon on the same port Vite expects or add a proxy; there is currently none configured in `vite.config.ts`.

## Build and embed

```bash
cd webui && pnpm build
cd .. && go build -o ~/bin/tn ./cmd/tn
```

`pnpm build` runs `vite build && tsc -b --noEmit` and emits into `webui/dist/`, which `webui/embed.go` (package `webui`) embeds via `//go:embed all:dist` and exports as `Dist embed.FS`, imported by the Go binary's `internal/tn/ui.go`. `webui/dist/` is committed to the repository specifically so a fresh checkout can `go build` immediately without Node or pnpm installed at all. You only need to run `pnpm build` when you've actually changed something under `webui/src/`.

> **Warning: the stale-bundle footgun.** `go build` embeds whatever bytes are on disk in
> `webui/dist/` at that moment. It does **not** check whether `webui/src/`'s TypeScript/React
> source has changed since the bundle there was last built. Edit a `.tsx` file, forget
> `pnpm build`, then run `go build`: the daemon compiles, signs, and serves a stale UI with
> zero warning, no version mismatch error, nothing. If `GET /ui` looks wrong after a change
> under `webui/`, this is the first thing to check.

### Checking for staleness

`/status.daemon.buildHash` is a short hash computed from the actual bytes embedded in the running binary (path + content of every file under `webui/dist`, hashed once at program init, see `computeWebUIBuildHash` in `internal/tn/ui.go`), rendered in the UI's own footer. Run a fresh `pnpm build` and compare: if the hash the running daemon reports doesn't match what a fresh build would produce, the running binary is stale.

If `webui/dist/` has *some* files but isn't a real Vite build (missing its `assets/` directory, since every real build of this app emits one), `GET /ui` serves a loud "Web UI not built" page telling you to run `pnpm build` rather than trying to serve a broken bundle. This does **not** catch a genuinely *empty* `webui/dist/` (e.g. someone deletes its contents): that fails at Go compile time instead (`//go:embed`'s "no matching files" error), which is already an immediate, self-explanatory failure with nothing further to engineer around.

## Where things live

- `src/routes/`: TanStack Router file-based routes (`index.tsx`, `agent.$name.tsx`, `project.$slug.tsx`, `feed.tsx`, plus `__root.tsx`). `routeTree.gen.ts` is generated by the `tanstackRouter` Vite plugin from this directory; don't hand-edit it.
- `src/lib/api.ts`: the daemon HTTP contract, TypeScript types kept in sync with the daemon's response shapes (`internal/tn/status.go`, `internal/tn/feed.go`, and the other handler files), plus fetch helpers (`fetchStatus`, `fetchFeed`, `postJson` and the action wrappers built on it: `approve`, `drain`, `retire`, `setSpawnPaused`, `sendReply`, `swapCredentials`).
- `src/lib/useEvents.ts`: subscribes to `GET /events` (server-sent events) and calls a callback whenever the daemon signals a mutation happened, so the caller can re-fetch `/status`. Reconnects with exponential backoff (starting at 1s, capped at 30s) on failure; polling (where used) is the fallback for when the stream can't be established at all.
- `src/lib/StatusContext.tsx`, `agentState.tsx`, `theme.ts`, `host.ts`: shared state and host-detection (standalone browser vs. the Obsidian plugin's iframe) plumbing.
- `src/components/ui/`: shadcn/ui components (`badge`, `button`, `card`, `separator`).

## The /status and /events contracts

`fetchStatus()` hits `GET /status` and returns a `StatusResponse` (typed in `api.ts`): daemon info (`uptime`, `version`, `pid`, `port`, `spawnPaused`, `vaultName`, `buildHash`), a `projects` map keyed by slug (each with its agents, queue counts, task-status counts, `maxOrchestrators`/`maxWorkers`), plus top-level `needsActionTasks`, `stuckPrompts`, `recentActivity`, and an optional `credentials` block (absent entirely on a daemon that predates credential profiles, or one with no credential store wired, in which case the UI simply shows no switcher).

`GET /events` is a Server-Sent Events stream: each message is a signal to re-fetch `/status`, not a payload carrying the new state itself. The client always re-fetches on receipt rather than trying to apply a partial update.

`GET /feed` (used by the `feed.tsx` route) returns a merged, newest-first timeline of message sends, acks, and activity-log entries; see the `FeedEntry` type in `api.ts`.
